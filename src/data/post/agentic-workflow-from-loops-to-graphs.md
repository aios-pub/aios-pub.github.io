> 本文整理自吴恩达（Andrew Ng）在 DeepLearning.AI 及 Sequoia AI Ascent 等公开场合关于 Agentic AI 的课程与演讲，为独立编译的学习笔记，与吴恩达本人及其机构无关联，亦未获其背书。文中基准数据均引自其公开分析。

## 核心结论：架构比模型更重要

吴恩达做过一个著名的对比实验：**GPT-3.5 在零样本（zero-shot）模式下只解决了 HumanEval 代码基准 48.1% 的题目，GPT-4 零样本为 67.0%；而当 GPT-3.5 被包裹进一个智能体工作流（Agentic Workflow）后，得分飙升到 95.1%**——超过了零样本的 GPT-4。

| 配置                        | HumanEval 得分 |
| --------------------------- | -------------- |
| GPT-3.5 零样本（zero-shot） | 48.1%          |
| GPT-4 零样本（zero-shot）   | 67.0%          |
| **GPT-3.5 + 智能体工作流**  | **95.1%**      |

换句话说，从 GPT-3.5 升级到 GPT-4 带来的提升，远远小于把模型放进一个允许迭代的工作流带来的提升。吴恩达因此判断：

> "AI 智能体工作流将推动今年 AI 的巨大进步——甚至可能超过下一代基础模型带来的进步。"

为什么不直接让大模型一次性输出？吴恩达的类比很日常：人类写文章也要打草稿、重读、删除、查证资料、调整段落、请人批评。而零样本调用的大模型通常被剥夺了所有这些机会。智能体设计的核心主张不是"直接提示没用"，而是：**当模型被放进一个允许迭代、取证、任务分解与角色分离的工作流后，很多任务的可靠性会大幅提升。**

## 四大设计模式

吴恩达将智能体工作流总结为四种设计模式：反思（Reflection）、工具调用（Tool Use）、规划（Planning）与多智能体协作（Multi-Agent Collaboration）。

### 第一步：反思（Reflection）

反思是一个迭代过程：大模型检查自己的输出，对照任务描述或评分标准（rubric）找出缺陷，然后产出修订版。实现上可以用同一个模型实例在"生成者"与"评审者"两种提示词之间切换，也可以用两个角色分离的实例——一个负责生成，一个负责评估。**关键不在于模型对象的数量，而在于存在显式的反馈回路和明确的停止规则（stopping rule）。**

机制上，反思至少需要四类产物：任务描述、当前草稿、评审意见、修订决策。最小闭环是：生成一次 → 请求结构化评审 → 修订 → 重复，直到评审者判定合格或达到迭代上限。

```python
@dataclass
class Critique:
    satisfactory: bool
    issues: list[str]
    revision_instructions: list[str]

def reflect(task: str, llm, max_iterations=3):
    draft = llm.generate(task)
    for _ in range(max_iterations):
        feedback = llm.evaluate(task=task, draft=draft)
        if feedback.satisfactory:
            return draft
        draft = llm.revise(task, draft, feedback)
    return draft
```

吴恩达的编程示例非常直接：一个编码智能体写完代码后，收到一段相当于"这是为任务 X 写的代码，请仔细检查其正确性、风格与效率"的提示。评审者往往能发现初稿忽略的 bug、缺失的边界条件或糟糕的结构，随后在不更换底层模型的前提下修复草稿。吴恩达评价反思模式"相当稳健——我几乎总能把它们调好"，并称其对应用效果的提升令他惊喜。

**最佳适用场景**：输出质量可以依据显式标准评估的任务——代码可以对照测试与风格规则检查，报告可以对照必需章节与来源覆盖检查，SQL 可以对照数据库模式与期望行数检查。当评审者并不比生成者拥有更好的信号时，该模式会失效。

实践要点：把"评审"与"重写"分开——先请求结构化的问题清单，再把清单喂给独立的修订步骤；要求评审者引用草稿、测试或源材料中的证据；设置迭代上限，否则反思回路会在无意义的风格微调上空耗 token。

**失败模式**：(1) 自我确认——评审者重复了产生草稿的同一套假设；(2) 评分标准漂移——评审者奖励的是流畅度而非任务正确性；(3) 非单调修订——修复一个问题的同时引入另一个。

### 第二步：工具调用（Tool Use）

工具调用让大模型能够选择并调用外部能力：网络搜索、代码执行、计算器、数据库、文件操作或应用 API。模型贡献语言理解与决策能力，工具贡献接地（grounding）的真实数据或确定性的动作执行。这种分工把系统扩展到了模型训练时记忆之外、也超出了自由文本能可靠计算的范围。

```python
@dataclass
class ToolCall:
    name: str
    arguments: dict

tools = {
    "web_search": search_web,
    "run_code": execute_python,
    "query_db": database_query,
}

def agent_with_tools(task, llm, tools, max_steps=10):
    context = [task]
    for _ in range(max_steps):
        action = llm.choose_action(context, tools)
        if action.name == "finish":
            return llm.synthesize(context)
        result = tools[action.name](**action.arguments)
        context.append({"tool": action.name, "result": result})
    return llm.synthesize(context)
```

能执行代码的模型可以验证自己的逻辑；能搜索的模型可以为论断找到事实依据；能访问数据库的模型可以给出精确答案而非统计意义上的近似。工具调用把大模型从一个会"幻觉"（hallucination）补全的封闭系统，变成了能对照现实检查自身工作的开放系统。

吴恩达指出，早期重要的工具调用工作来自计算机视觉社区，因为语言模型无法直接操作图像——"唯一的办法是让 LLM 生成一个函数调用来操作图像，比如生成图像或做目标检测"。如今同样的架构已经支撑起广泛得多的动作空间。

**失败模式**：(1) 选错工具——需要查询数据库时却调用了搜索；(2) 参数非法——传入格式错误的输入；(3) 盲信工具输出——不对结果做校验；(4) 工具滥用——上下文已足够时仍然调用工具。控制手段：类型化的工具模式（tool schema）、参数校验、结果确认、权限边界。

### 第三步：规划（Planning）

规划让大模型自主决定执行哪些步骤序列来完成更大的任务。例如被要求就某个主题做在线调研时，模型会把目标拆解为子任务：调研各个子话题、综合发现、编写报告。

吴恩达描述过一次现场演示：他的调研智能体的网络搜索 API 返回了限流（rate limiting）错误。"让我惊讶的是，智能体敏捷地转向了维基百科搜索工具——我都忘了自己给过它这个工具——然后用维基百科替代网络搜索完成了任务。这对我来说是一个 AI 智能体的'惊喜时刻'。"他也提到日常用法："有一项研究我自己懒得去 Google，就丢给调研智能体，几分钟后回来看看它做了什么。"

```python
def plan_and_execute(objective, llm, tools, budget):
    plan = llm.create_plan(objective)  # JSON 结构化步骤
    results = []
    for step in plan.steps:
        result = execute_step(step, tools, results)
        results.append(result)
        if result.failed:
            plan = llm.replan(objective, results, remaining_budget=budget)
    return llm.synthesize(results)
```

对成熟度，吴恩达很坦率："更前沿——有时它们的表现让我大开眼界，但至少目前，我没法保证总能可靠地跑通。"实践含义是：规划型智能体需要比反思回路更紧的约束——结构化的计划格式、依赖校验、有界的步骤数、兜底策略。

**失败模式**：(1) 过度规划——为简单任务生成庞大计划；(2) 计划与执行脱节——计划里写了智能体实际做不了的步骤；(3) 级联失败——一步出错污染后续所有步骤；(4) 无界重规划——无限重排计划却不收敛。控制手段：执行前校验依赖、跨重规划保留已完成的有效工作、限制总步数。

### 第四步：多智能体协作（Multi-Agent Collaboration）

多智能体协作让多个大模型实例参与，各自被赋予不同角色的提示词，共同完成受益于专业化分工、独立交叉验证或并行覆盖的任务。

吴恩达常举 ChatDev 的例子："完全开源，在我的笔记本上就能跑。"系统提示同一个 LLM 有时扮演软件工程公司的 CEO，有时是设计师、产品经理或测试工程师。"这群智能体会协作、进行长对话——你让它'请开发一个围棋游戏'，它们真的会花几分钟写代码、测试、迭代，然后生成复杂得惊人的程序。"他还提到多智能体辩论（debate）："让不同的智能体互相辩论确实能带来更好的性能。让多个模拟的 AI 智能体协同工作，已被证明是一种强大的设计模式。"

```python
agents = {
    "coder": Agent(role="senior software engineer"),
    "reviewer": Agent(role="expert code reviewer"),
    "tester": Agent(role="QA engineer"),
}

def multi_agent_build(spec, agents, max_rounds=3):
    code = agents["coder"].implement(spec)
    for _ in range(max_rounds):
        review = agents["reviewer"].critique(code)
        tests = agents["tester"].write_and_run(code)
        if review.approved and tests.passed:
            return {"code": code, "tests": tests}
        code = agents["coder"].revise(
            spec=spec, code=code, review=review, test_result=tests)
    return {"code": code, "status": "limit_reached"}
```

吴恩达称多智能体协作同样"更前沿"，但"效果比你想的好得多"。该模式的典型败因：冗余智能体（所有智能体看到同样的证据、优化同样的评分标准）、群体思维（groupthink）、对话过长、协调开销。**智能体数量增多并不会自动带来更多智能。**

实践要点：为每一次交接（handoff）定义产物契约（artifact contract）。调研者返回带来源的论断，规划者返回类型化步骤，编码者返回代码与假设，评估者返回缺陷与决策。智能体之间应通过产物与共享状态通信，而不是无限制的对话历史。这一约束也是通往图架构的准备。

| 模式                 | 成熟度 | 吴恩达的评价           |
| -------------------- | ------ | ---------------------- |
| 反思 Reflection      | 稳健   | "我几乎总能把它们调好" |
| 工具调用 Tool Use    | 稳健   | 已广泛部署、理解充分   |

## Anthropic 的五种生产级工作流

Anthropic 在《Building Effective Agents》中区分了**工作流**（LLM 与工具按预定义代码路径运行）与**智能体**（模型动态指挥自己的过程）。这个区分的价值在于抵抗不必要的自主性：许多可靠系统用简单、可组合的工作流就能构建，只有任务真正需要自适应时才引入动态智能体。

1. **提示链（Prompt Chaining）**：把一次 LLM 调用的输出按固定顺序送入下一次。每个阶段只做窄域转换，阶段之间可以插入程序化检查。适用于能"干净利落地分解为固定子任务"的任务。优点是可预测、各阶段可独立测试；缺点是对意外输入不灵活。
2. **路由（Routing）**：对输入分类，送往专门的提示词、工具集、模型或工作流。例如客服系统把账单问题路由给账单智能体、技术故障路由给诊断工作流。主要失败模式是误分类，控制手段包括置信度阈值与兜底路由。
3. **并行化（Parallelization）**：同时运行多次 LLM 调用再聚合输出。两个变体：分片（sectioning，独立子任务分给多个工作者）降低延迟；投票（voting，同一任务跑多次、由聚合器选最优）提升稳健性。注意：同一个模型用几乎相同的提示词生成十份输出，并不等于十个独立判断。
4. **编排者-工作者（Orchestrator-Workers）**：由一个中央 LLM 分析任务、动态创建子任务、委派给工作者并综合结果。它组合了规划与多智能体协作，强大之处在于自适应，但编排者可能成为上下文瓶颈。实践上应要求工作者返回结构化产物而非原始对话。
5. **评估器-优化器（Evaluator-Optimizer）**：把生成与评估分开——一个 LLM 生成响应，另一个对照显式标准评估，生成者修订，循环直至达标。这其实就是反思模式以显式角色分离的形式固化成生产工作流，对翻译、代码、受政策约束的写作与结构化文档尤其有效。

**两套模式如何对应：**

| 吴恩达模式 | Anthropic 工作流            | 关键增量               |
| ---------- | --------------------------- | ---------------------- |
| 反思       | 评估器-优化器               | 显式角色分离与停止标准 |
| 工具调用   | 增强型 LLM（Augmented LLM） | 一切工作流的构建基块   |
| 规划       | 编排者-工作者 + 提示链      | 动态分解 vs 固定分解   |
| 多智能体   | 并行化 + 编排者-工作者      | 生产级编排             |

**生产默认原则**：永远从能满足任务的最简单模式开始。简单问答用直接调用；步骤固定用链；请求类别清晰用路由；需要独立覆盖用并行；分解方式需要现场发现用编排者；质量可判定且可迭代改进用评估器-优化器。每上一级，都会增加成本、延迟、非确定性与失败模式。智能体设计的有效性体现在"因观察到的错误而增加复杂度"，而不是"一开始就把所有模式堆上去"。

## 从循环到图：架构的四个阶段

把两套模式词汇放在一起，可以看到状态、控制与职责组织方式的递进。这不是每个项目都必须爬完的成熟度阶梯——很多任务就应该停留在直接调用或固定链上。

**循环阶段（Loop）**：一个智能体反复检查、修订自己的工作，反思是核心机制，常配合工具使用。循环紧凑、易于原型验证，适合装进单个上下文窗口（context window）的任务。当任务包含太多证据、太多独立关注点或太多历史时，循环开始崩溃——每次迭代都可能重发任务、草稿、评审、工具结果与历史决策，上下文变得昂贵而嘈杂。

**链阶段（Chain）**：把工作拆成固定顺序的专业化转换，把"顺序"外化到应用代码中。每个阶段可以有自己的提示词、模型、工具与校验。相比反思回路，链更可预测，因为路径是已知的；代价是必须预想到所有意外情况。

**网络阶段（Network）**：引入多个角色专业化的工作者。编排者委派、工作者执行、结果回传综合。核心限制是上下文管理——正如 Anthropic 指出的："当上下文复杂到单个智能体无法有效管理时，智能体难以维持一致性，形成性能瓶颈。"编排者可能沦为接收每个工作者完整输出的"对话枢纽"。

**图阶段（Graph）**：把共享状态外化为一个持久、可查询的结构。每个工作者只读取与其任务相关的子图，并把新的实体与关系写回。编排者的上下文保持精简，共享状态活在图里，任何智能体随时可查。

知识图谱在多智能体系统中扮演三种角色：

- **编排者-工作者的共享记忆**：工作者直接对图读写，编排者的窗口保持干净。这是 Anthropic"会话不等于上下文窗口"原则的多智能体版本。
- **评估器-优化器的事实锚定层**：评估者对照带显式溯源（provenance）的图谱边来核查论断，反馈从"这看起来不太对"变成"三元组（X, 任职于, Y）在图中不存在"。
- **循环的持久世界模型**：图在上下文窗口冲刷后依然存在，就像状态文件在进程重启后依然存在。智能体会遗忘，图不会。

**最小图模式（schema）**可以从五类节点起步：实体（Entity，人物/组织/产品/概念）、论断（Claim，可能被支持或反驳的陈述）、来源（Source，文档/API 响应/测试结果）、产物（Artifact，计划/草稿/代码/报告）、运行记录（Run）。边刻画关系：提及（mentions）、支持（supports）、反驳（contradicts）、派生自（derived_from）、取代（supersedes）。每条论断保留溯源，每次修订指向前一版本。最小写操作应当是**增量式**的：不静默覆盖论断，而是创建新版本并用 supersedes 链接；不删除矛盾证据，而是保留双方论断并附上评估。

**图架构不等于自动正确**。图保存错误与保存事实一样高效：实体对齐（entity resolution）可能把不同组织合并成一个，抽取可能挂错日期，过度自信的评估者可能把弱来源标记为充分。因此图接地的系统需要数据质量机制：模式校验、规范化标识符、溯源、冲突显式表示、置信度校准与周期性审查。

## 落地路线图：从第一天到第一个月

推荐路径是从最小可靠循环起步，每次只加一种能力。每个阶段都应有基线、任务级指标、成本预算与回滚方案。

| 步骤         | 时间   | 复杂度 | 预期收益        |
| ------------ | ------ | ------ | --------------- |
| 加入反思     | 1 天   | 低     | 质量提升 10–30% |
| 加入工具调用 | 1 天   | 低     | 全新能力        |
| 规划智能体   | 1 周   | 中     | 攻克复杂任务    |
| 多智能体     | 2 周   | 中     | 更高质量        |
| 图架构       | 1 个月 | 高     | 持久化、可扩展  |

- **第一天：反思。** 选一个输出可评估的现有 LLM 调用，加一个对照显式评分标准做评审的第二次调用，把评审喂给修订调用，对比基线。生产环境应像下面这样记录每次反思的完整产物：

```json
{
  "task_id": "case-017",
  "draft_version": 1,
  "rubric_version": "support-v3",
  "issues": [
    { "type": "missing_evidence", "severity": "high" },
    { "type": "tone", "severity": "low" }
  ],
  "decision": "revise",
  "iteration": 1,
  "max_iterations": 3
}
```

- **第二天：工具调用。** 给智能体至少一个工具（代码执行或网络搜索），让它自己决定何时使用；纳入结果前先校验。留意吴恩达描述的"绕过故障改走他路"时刻。
- **第一周：规划智能体。** 复杂任务先让 LLM 以结构化 JSON 写计划再执行；步骤失败时带着"哪些已成功"的上下文重规划，并保留已完成的工作。
- **第二周：多智能体。** 至少拆出"生成者 + 评审者"两个角色，用同一个模型、不同系统提示词；为每次交接定义产物契约。
- **第一个月：接入图。** 在智能体运行之间加持久状态，从共享 JSON 文件或数据库起步；当智能体需要跨会话串联事实时，升级为知识图谱，并加上溯源跟踪与版本历史。

## 决策框架：什么时候用什么模式

| 场景               | 首选     | 原因                   |
| ------------------ | -------- | ---------------------- |
| 想要更好的输出质量 | 反思     | 最便宜、最可靠的改进   |
| 需要外部数据       | 工具调用 | 把答案锚定在真实信息上 |
| 复杂多步任务       | 规划     | 分解为可控步骤         |
| 需要多视角         | 多智能体 | 不同角色捕获不同错误   |
| 跨会话状态         | 图架构   | 在上下文窗口冲刷后存活 |
| 简单单轮问答       | 零样本   | 不要过度工程           |

经验法则：**当前模式的失败模式已被理解、且下一模式正好解决这个失败时，才加它；失败模式还不清楚时，先度量再增加复杂度。** 能满足任务的最便宜模式，通常就是对的那个。

## 一个容易被忽视的洞察：推理速度是乘数

吴恩达特别强调快速 token 生成对智能体工作流的意义，因为在这个范式里，LLM 生成的 token 是给其他 LLM 读的，不是给人读的："能以远超人类阅读速度的速度生成 token 太棒了。"即使质量略低的模型，只要出 token 快，"让你能在这个循环里多跑很多圈"，效果可能胜过更慢的更好的模型。这使得快速推理（优化的推理服务、量化模型）成为智能体系统性能的直接乘数。

他还说过一句关于使用姿势的话："我们需要学会把任务委派给 AI 智能体，然后耐心等待几分钟甚至几小时——就像新手经理派了活五分钟就去催，那没有生产力。"

## 局限与清醒剂

三点局限值得直说。其一，吴恩达本人把规划与多智能体称为"前沿"——它们并不总是好用。其二，智能体工作流用延迟换质量。其三，每次循环迭代都要花 token：如果所有智能体看到同样的证据、优化同样弱的标准，系统只是把同一个错误用更高的成本重复了多遍。

另外，HumanEval 是一个代码基准，95.1% 这个数字不应被默认迁移到所有领域。团队应当构建自己的评估集，在自己的场景里度量提升。

## 结语

**吴恩达的四个模式是词汇，Anthropic 的五种工作流是语法，图是语言。** 最重要的单点结论是：工作流架构比模型能力更重要——GPT-3.5 加智能体工作流（95.1%）胜过零样本的 GPT-4（67.0%）。

构建路径是增量的：从反思开始（它今天就能可靠地工作），加工具把答案锚定到真实数据，为复杂任务建规划智能体，当专业化带来可度量的信号时上多智能体，当状态必须跨会话持久、智能体需要共享世界模型时接入图。每种模式分别解决上一阶段的一个特定局限：反思解决单次生成的错误，工具解决知识缺口，规划解决复杂度，多智能体解决视角局限，图解决记忆局限。这条路径不是强制性的，但方向是明确的。

一个可靠的智能体系统应该让下面这句话为真：**每一个重要输出，都可以追溯到一项任务、一份计划、一个产物、一个来源、一个评估决策和一条有界执行记录。** 当这句话为真时，循环、工具、计划、工作者与图就是可组合的工程机制，而不是不可解释的黑盒行为。从循环到图，不是从简单到复杂，而是从隐式状态到显式状态、从易失内存到持久内存、从估计到证据。

正如吴恩达所说："通往 AGI 的路更像一场旅程而不是一个终点，而这类智能体工作流，能帮助我们在漫长的旅途中向前迈出一小步。"
